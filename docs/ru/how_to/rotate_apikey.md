# Ротация API-ключа

Каждый публичный `ApiKey` стоит периодически ротировать: при утечке,
уходе сотрудника или по фиксированному графику (90 дней — разумный
дефолт).

`dbmail` поставляет два admin action и shell-путь. Оба сохраняют
идентичность строки (внешние ключи на `MailLog.user` и т.д.
остаются целы); меняются только `ApiKey.api_key` и
`ApiKey.password_hash`.

## Через admin

1. Откройте `/admin/dbmail/apikey/`.
2. Отметьте ключи для ротации.
3. **Меню Action → "Rotate selected API keys"** → Go.
4. Сообщение об успехе один раз покажет новые сырые значения —
   скопируйте сразу. После редиректа ключи маскируются.

Action `rotate_api_key` вызывает `secrets.token_urlsafe(24)[:32]` на
каждую строку, ставит `api_key=<new>`, обнуляет `password_hash` и
сохраняет. `save_model` пере-хеширует на следующем запросе.

## Через shell

```python
import secrets
from dbmail.models import ApiKey

key = ApiKey.objects.get(name="my-app")
new_raw = secrets.token_urlsafe(24)[:32]
key.api_key = new_raw
key.password_hash = ""    # принудительный re-hash при save
key.save()
print("Новый сырой ключ:", new_raw)
```

`ApiKey.save()` пересчитывает `password_hash` из `api_key`, если
хеш пуст — см. `dbmail/models.py:ApiKey.save`.

## Ротация без даунтайма (один ключ на двух клиентах)

Если строка `ApiKey` используется двумя сервисами и нужен ноль
даунтайма:

1. **Добавьте** вторую `ApiKey` (`name="my-app-rotation"`) с новым
   сырым значением. Передайте её в первый сервис.
2. **Дождитесь**, пока он полностью переключится на новый ключ
   (проверяйте через `last_used_at` старой строки).
3. Передайте новый ключ во второй сервис.
4. **Отзовите** старую строку: отметьте в admin, **Action → "Revoke
   selected API keys"** (ставит `is_active=False` — **не** удаляет,
   audit-история сохраняется).
5. Через 30 дней удалите отозванную строку полностью.

Это избегает гонки при инвалидации кеша, которую создаёт ротация
одной строкой — старый хешированный ключ кешируется до истечения
`DB_MAILER_CACHE_TTL`; до этого аутентифицируются и старый, и
новый.

## Инвалидация кеша

`ApiKey.save()` сбрасывает per-key cache entry
(`dbmail:apikey:<sha256(raw)>`) — следующий запрос ре-валидирует
против нового хеша. Если ротируете через сырой SQL `UPDATE` (не
рекомендуется), вызовите:

```python
from dbmail.models import ApiKey
ApiKey.clean_cache()
```

…это очистит весь namespace `dbmail:apikey:*`.

## Аудит

`ApiKey.last_used_at` и `last_used_ip` заполняются на каждой
успешной аутентификации (cache miss). После ротации они сбрасываются
на `None` до первого использования нового ключа.

`MailLog.user` ссылается на Django-пользователя, не на `ApiKey` —
исторической связи "эта строка отправлена под каким ключом" нет.
Если нужно — логируйте в кастомном Sender override или post-save
сигнале на `MailLog`.
